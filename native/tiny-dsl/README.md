# tiny-dsl

`tiny-dsl` parses Badbox's versioned rule language into a Rust syntax model.

The crate does not check source code and does not depend on ast-grep. Badbox lowers its output into
the engine-owned Rule IR, then the selected structural backend compiles and executes that IR.

```text
.badbox source -> tiny-dsl parser -> Badbox Rule IR -> ast-grep backend -> findings
```

The crate is currently an internal path dependency of `badbox-native`; it is not published
separately.

## Complete example

```text
#badbox 1

rule rust/excessive-clones for rust {
  summary "Excessive clone calls within one callable"

  param limit = 4

  find code(value) `value.clone()`
  group by nearest callable
  when count > limit

  report {
    severity info
    message "Callable contains more clone call sites than the configured limit"
    evidence "clone call sites"
  }
}

test rust/excessive-clones "reports excessive clones" {
  input "fixtures/excessive.rs"
  expect {
    findings 1
    count 5
  }
}

test rust/excessive-clones "accepts limited clones" {
  input "fixtures/acceptable.rs"
  expect findings 0
}
```

One file may contain multiple `rule` and `test` blocks. A directory passed as a Badbox rule path
is a pack: Badbox recursively loads its `.badbox` files in deterministic path
order. Rule IDs must remain unique across the complete check.

## File version

Every file starts with the header generated by `badbox create <name.badbox>`:

```text
#badbox 1
```

The version belongs to the DSL syntax, not to an individual rule. Users should
not choose it manually. Unsupported versions are errors.

## Rules

```text
rule namespace/name for language {
  ...
}
```

IDs use lowercase letters, digits, and hyphens and contain exactly one `/`. For example,
`rust/excessive-clones` is valid.

A rule requires one `summary`, `find`, `group`, `when`, and `report` entry. `param` and `where`
entries may repeat. Other duplicate or unknown entries are errors.

### Parameters

Parameters are rule-local scalar values whose type is inferred:

```text
param limit = 4
param enabled = true
param label = "clone call sites"
```

The count condition currently accepts an unsigned integer literal or an integer parameter:

```text
when count > 4
when count > limit
```

Text conditions accept string parameters wherever they accept a string literal:

```text
param method = "clone"
where text(name) == method
where text(name) in ["unwrap", method]
```

Integer and boolean parameters cannot be used in text conditions. Boolean parameters are accepted
and overridable but no condition reads them yet.

Callers override a parameter with its qualified key:

```ts
await inspect({
  paths: ["src"],
  rulePaths: [".badbox"],
  parameters: { "rust/excessive-clones.limit": 8 },
});
```

Unknown parameters and values of the wrong inferred type are errors. Parameter values cannot replace
patterns, node kinds, or other structural rule syntax. Effective values participate in Badbox's
native result-cache fingerprint.

### Structural selection

Use source-shaped code when the pattern is easiest to recognize as code:

```text
find code(value) `value.clone()`
find code(callee, args...) `callee(args)`
```

Names declared inside `code(...)` are captures. The declaration is what makes a name a hole;
undeclared identifiers in the backtick pattern remain literal. `name...` declares a multiple-node
capture. Badbox lowers declared names to the backend's capture notation before compilation.
Capture names start with a letter and contain only letters, digits, and underscores.

Capture names are rule-scoped for ordering relations. Repeating a single-node capture name in the
primary selector and an ordering selector (`follows`, `precedes`, `not follows`, or `not precedes`) requires both occurrences to capture exactly
the same source text. Different names remain independent. Repeating a primary capture name in a
`has`, `lacks`, `inside`, or `not inside` selector is rejected because those relations do not correlate captures.

Use an explicit syntax-node kind when the grammar already has a precise node:

```text
find node go_statement
```

Some code parses differently on its own than in a real file. In C, `free(pointer);` alone is a
declaration, so `` code(pointer) `free(pointer)` `` matches no calls. Write the code inside a
context where it parses as intended and select the node kind to match:

```text
find code(pointer) `void f() { free(pointer); }` select call_expression
```

The pattern is the first `call_expression` in the context, in depth-first order; the rest of the
context only shapes parsing. A context without a node of the selected kind is an error. `select` works wherever `code(...)` does, including relational selectors.

### Ownership

Findings are grouped under their nearest owning scope:

```text
group by nearest callable
```

`callable` is intentionally semantic. Closures, lambdas, and nested functions are callables of their
own, so a site inside one belongs to it rather than to the enclosing function. Badbox maps
`callable` for these languages:

| Language | Node kinds |
| --- | --- |
| Rust | `function_item`, `closure_expression` |
| Go | `function_declaration`, `method_declaration`, `func_literal` |
| PowerShell | `function_statement` |
| Zig | `function_declaration` |
| TypeScript, TSX, JavaScript | `function_declaration`, `generator_function_declaration`, `function_expression`, `generator_function`, `arrow_function`, `method_definition` |
| Python | `function_definition`, `lambda` |
| Java | `method_declaration`, `constructor_declaration`, `compact_constructor_declaration`, `lambda_expression` |
| C | `function_definition` |
| C++ | `function_definition`, `lambda_expression` |
| C# | `method_declaration`, `constructor_declaration`, `destructor_declaration`, `local_function_statement`, `lambda_expression`, `anonymous_method_expression`, `accessor_declaration`, `operator_declaration` |
| PHP | `function_definition`, `method_declaration`, `anonymous_function`, `arrow_function` |
| Lua | `function_declaration`, `function_definition` |
| Kotlin | `function_declaration`, `anonymous_function`, `lambda_literal`, `secondary_constructor` |
| Swift | `function_declaration`, `init_declaration`, `deinit_declaration`, `lambda_literal` |
| Dart | `function_declaration`, `method_declaration`, `local_function_declaration`, `getter_declaration`, `setter_declaration`, `function_expression` |
| Bash | `function_definition` |
| Ruby | `method`, `singleton_method`, `lambda`, `block`, `do_block` |

Ruby blocks such as `items.each do ... end` are callables, so their sites do not count toward the
enclosing method. A Ruby `-> { ... }` lambda's body is a `block`, which is therefore its nearest owner.

Other languages reject `callable` with an error. For them, or whenever exact control is preferable,
use raw node kinds:

```text
group by nearest node(function_item, closure_expression)
```

### Conditions

Version 1 aggregates distinct selected ranges per owner and compares the exact count:

```text
when count > limit
```

The comparison is strictly greater-than.

### Reporting

```text
report {
  severity warning
  message "Callable contains too many clone call sites"
  evidence "clone call sites"
}
```

Severity is `info`, `warning`, or `error`. It labels evidence; a finding does not automatically make
the Badbox process fail.

Messages can contain placeholders:

```text
param limit = 4
...
message "Callable has {count} clone calls (limit {limit})"
```

- `{count}` is the finding's observed count.
- `{name}` is the value of a declared parameter after overrides. The count threshold parameter shows
  the threshold the check applies.
- `{{` and `}}` are literal braces.

An unknown placeholder, an unclosed `{`, a lone `}`, and `{count}` in a rule that also declares a
parameter named `count` are lowering errors. Captures are not interpolated: a finding aggregates
many matches, so a single captured value would be ambiguous.

## Relational conditions

Badbox executes capture predicates and a bounded set of structural evidence clauses:

```text
where text(method) in ["unwrap", "expect"]

where group lacks any {
  code(ctx) `ctx.cancel()`
  node select_expression
}

find code(statement) `statement.clearBindings()`
where match follows any {
  code(statement) `statement.reset()`
}
```

Text operators are `==`, `!=`, `in`, `not in`, and `matches`. The capture must be declared by the
rule's `find code(...)` selector. `matches` uses Rust regular-expression syntax.

The evaluator currently supports these structural combinations:

- `where match inside any|all { ... }` requires the selected match to be inside the auxiliary
  selector or selectors. A match is not inside itself; an enclosing node of another kind with the
  same range still counts.
- `where match not inside any|all { ... }` requires the match not to satisfy the corresponding
  `inside` condition. `not inside any` means inside none of the selectors; `not inside all` means
  outside at least one of them.
- `where group has any|all { ... }` requires the owning group to contain matching evidence.
- `where group lacks any|all { ... }` requires the owning group not to satisfy the corresponding
  `has` condition.
- `where match follows any|all { ... }` requires qualifying auxiliary statements before the
  selected statement.
- `where match precedes any|all { ... }` requires qualifying auxiliary statements after the
  selected statement.
- `where match not follows any|all { ... }` and `where match not precedes any|all { ... }` require
  the match not to satisfy the corresponding `follows` or `precedes` condition. `not precedes any`
  means no listed selector has a qualifying statement after the match; `not precedes all` means at
  least one of them has none. A match outside any statement list satisfies both negations.

Repeated `where` clauses mean all clauses must hold. Badbox collects the primary and auxiliary
structural matches in one syntax-tree traversal per file, then evaluates the relations from their
ranges. Identical selectors are collected once and shared by every rule that references them; it
does not rescan an owner for every primary match.

Ordering relations require `group by nearest callable`. Primary and auxiliary matches must
resolve to statements in the same lexical block and to the same nearest callable. Intervening
sibling statements are allowed. Nested callables and different branch, loop, switch, or
error-handling blocks do not satisfy the relation. `any` means at least one listed selector has a
qualifying occurrence; `all` means every listed selector does. Immediate-sibling ordering is not
implemented. When a capture name occurs in both the primary and an ordering selector, exact captured
source-text equality is an additional requirement. Multiple shared names must all match;
multiple-node captures cannot be correlated. Capture values are interned only for the current file
and are discarded after evaluation. Other target/relation combinations are rejected rather than
silently ignored.

A lexical block is one of the language's statement-list nodes:

| Language | Statement lists |
| --- | --- |
| Rust, Zig | `block` |
| Go, PowerShell | `statement_list` |
| TypeScript, TSX, JavaScript | `statement_block`, `switch_case`, `switch_default` |
| Python, Lua | `block` |
| Java | `block`, `constructor_body`, `switch_block_statement_group` |
| C, C++ | `compound_statement`, `case_statement` |
| C# | `block`, `switch_section` |
| PHP | `compound_statement`, `colon_block`, `case_statement`, `default_statement` |
| Kotlin, Swift | `statements` |
| Dart | `block`, `switch_statement_case`, `switch_statement_default` |
| Bash | `compound_statement`, `do_group`, `case_item` |
| Ruby | `body_statement`, `block_body`, `then`, `else`, `do`, `begin`, `ensure` |

Each switch case is its own list, so statements in different cases never satisfy each other. A body
without a statement-list node belongs to the statement that contains it. Examples are a braceless
`if (flag) target();` in C-family languages and Bash `if` bodies. So `prepare(); if (flag) target();`
satisfies `follows`, while `prepare(); if (flag) { target(); }` does not.

## Tests and fixtures

Tests live in the DSL and source code lives in external fixture files:

```text
test rust/excessive-clones "reports excessive clones" {
  input "fixtures/excessive.rs"
  expect {
    findings 1
    count 5
  }
}
```

`findings` is required. `count` checks the observed count of the single expected finding, so it is
allowed only with `findings 1`. A test must name a rule declared in the same file. `input` is
relative to the rule file.

`badbox test` checks each fixture against only its own rule file and the named rule. A test fails
when the counts differ, or when the fixture is missing, has syntax errors, or is not a source file
of the rule's language.

## Comments and literals

The required first line starts with `#badbox`; elsewhere, `#` starts a line
comment outside strings and code patterns. Strings use double quotes and support
`\"`, `\\`, `\n`, and `\t`. Structural code uses backticks; write `\`` for a literal backtick.

## Rust API

```rust
let document = tiny_dsl::parse(source)?;
for rule in document.rules {
    println!("{}", rule.id);
}
```

`parse` returns a `Document` or a `ParseError` containing a source line and column. The public syntax
types contain owned data so Badbox can cache or lower a parsed document without retaining the input
buffer.

## Current boundaries

- The crate parses rules and tests; it does not read files or execute tests. Badbox runs them.
- Badbox executes `find -> where -> group -> count -> threshold -> report`, including text
  predicates, `match inside`, `match not inside`, `group has/lacks`, `match follows/precedes`, and
  `match not follows/not precedes`.
- Statement ordering executes for every language with a `callable` mapping. Immediate ordering and
  unsupported target/relation combinations are rejected by the scanner.
- `callable` has semantic mappings for Rust, Go, PowerShell, Zig, TypeScript, TSX, JavaScript,
  Python, Java, C, C++, C#, PHP, Lua, Kotlin, Swift, Dart, Bash, and Ruby. Other languages use
  explicit `node(...)` ownership.
- PowerShell code patterns support single-node declared captures; multiple captures are rejected.
- The DSL is Badbox's only rule format. A `.yaml` rule file passed directly is rejected; rule packs load only `.badbox` files.
